# 계약 — 세그먼트 인덱스 (1번 ↔ 3번)

> For future Claude: PokeClip **세그먼트 인덱스 계약**. 인덱스는 **매니페스트 생성의 단일 진실원**이며 **S3 LIST를 대체**한다(LIST는 느림·비쌈·즉시일관성 문제·길이 정보 없음). 방향은 **1↔3 상호** — 스키마 소유는 3번(데이터 계층 오너), 쓰기·읽기 주체는 1번(Media Origin/업로더). 파라미터 근거 [ADR-020](adr/ADR-020_LLHLS_DVR파라미터.md), 일반개념 llhls-dvr-and-delivery §5, 티어링 근거 [ADR-004](adr/ADR-004_DVR_VOD보관.md)·[ADR-005](adr/ADR-005_저장일원화.md)·[ADR-015](adr/ADR-015_CDN_CloudFront확정.md). **초안(2026-07-25) — 컬럼 타입·인덱스 전략은 3번 리뷰 후 확정.**

## 1. 왜 필요한가 (설계 불변식)

- **매니페스트는 인덱스에서 생성한다. S3 LIST 금지.** 이유: ① LIST는 1000개씩 페이지네이션 + 요청당 과금 ② 갓 올린 객체가 목록에 늦게 뜰 수 있음(라이브에 치명) ③ **LIST는 키만 주고 세그먼트 길이(`#EXTINF`)를 모른다**.
- **길이는 세그먼트를 만든 쪽이 기록**한다(정확). 인덱스가 그 값을 보관한다.
- **티어 경계(hot/cold)와 업로드 확인 게이팅이 이 테이블 하나로 판정**된다([ADR-020](adr/ADR-020_LLHLS_DVR파라미터.md) §2).

## 2. 스키마 (초안 — 합성 예시값)

테이블 `stream_segments`

| 필드 | 타입(제안) | 설명 |
|---|---|---|
| `stream_id` | text/uuid | 방송 스트림 식별자. `broadcasts`와 FK |
| `seq` | bigint | 세그먼트 시퀀스(스트림 내 단조 증가). **PK = (stream_id, seq)** |
| `start_pts_ms` | bigint | 스트림 기준 시작 위치(ms). 매니페스트 정렬·DVR 창 계산 기준 |
| `start_wall_utc` | timestamptz | 실제 시작 시각 **UTC(ISO-8601)**. 표시·클립 구간 매핑용. **로컬 타임존 저장 금지**([ADR-020](adr/ADR-020_LLHLS_DVR파라미터.md) §2) |
| `duration_ms` | int | 세그먼트 길이(ms). `#EXTINF` 값의 출처. 목표 4000, **실측값** 기록 |
| `s3_key` | text | 콜드 티어 객체 키 |
| `local_path` | text nullable | 핫 티어 로컬 경로(보관 중에만) |
| `upload_state` | enum | `pending` \| `uploaded` \| `failed`. **`uploaded`만 cold로 광고 가능** |
| `uploaded_at` | timestamptz nullable | 업로드 확인 시각(UTC) |
| `bytes` | int nullable | 객체 크기(검증·비용 분석) |
| `is_discontinuity` | bool | 앞 세그먼트와 불연속(재연결·인코딩 변경) → 매니페스트에 `EXT-X-DISCONTINUITY` |

**합성 예시 행**
```
stream_id      = "demo-stream"
seq            = 123
start_pts_ms   = 492000
start_wall_utc = 2026-07-25T01:23:45Z
duration_ms    = 4000
s3_key         = "streams/demo-stream/2026-07-25/10/seg_000123.m4s"
local_path     = NULL
upload_state   = "uploaded"
uploaded_at    = 2026-07-25T01:23:50Z
bytes          = 812345
is_discontinuity = false
```

**조회 패턴(인덱스 설계 근거 — 3번 확인 요청)**
- `WHERE stream_id = ? ORDER BY seq DESC LIMIT 900` — 라이브 매니페스트(DVR 1h)
- `WHERE stream_id = ? AND start_pts_ms BETWEEN ? AND ?` — 클립 컷 구간 조회
- `WHERE stream_id = ? AND upload_state = 'pending'` — 업로드 지연 감시
- `WHERE stream_id = ? ORDER BY seq DESC LIMIT 1` — **헬스 신선도 판정**(2026-07-27 헬스 2계층): live 방송의 마지막 created가 ~4s 내 갱신되는지 = 기능 생존 신호. created 멈춤=인제스트 사망 / pending 적체=업로드 경로 사망 구분. Auth 재배정 판단 입력

## 3. 상태 전이 (쓰기 주체 = 1번)

```
세그먼트 완성 →  INSERT (upload_state='pending', local_path 채움, s3_key 예약)
S3 업로드 성공 → UPDATE upload_state='uploaded', uploaded_at=now()
업로드 실패    → UPDATE upload_state='failed'   (재시도 후에도 실패 시 알람)
로컬 정리      → UPDATE local_path=NULL         (그레이스 지난 뒤에만)
```

**참고(2026-07-27):** 업로드는 **세그먼트 완성 즉시**(배칭 폐기 — [ADR-014](adr/ADR-014_비용모델.md) 갱신). 장애 유실 창 ≈ 세그먼트 1개(4s).

**불변식**
1. **`upload_state='uploaded'` 이전에는 cold URL로 광고하지 않는다.** 티어 경계 = `min(시계 목표, 마지막 uploaded seq)` — 위반 시 매니페스트가 404를 가리킨다([ADR-020](adr/ADR-020_LLHLS_DVR파라미터.md) §2).
2. **로컬 삭제는 광고 창보다 늦게.** 로컬 보관 8분(120개) > hot 광고 5분(75개) = **그레이스 오버랩**. `local_path=NULL` 처리는 그레이스 경과 후. **[갱신 2026-07-27] 삭제 조건 = `(그레이스 경과) AND (upload_state='uploaded')`, 세그먼트별 독립 평가** — 순서 개념 없음 → 업로드 밀린 세그먼트가 뒤 세그먼트 축출을 막는 head-of-line 블로킹이 구조적으로 없고, 밀린 놈만 홀로 남는다(개당 ~4MB). 백로그 감시는 디스크 워터마크 알람. 정규 URL+failover([ADR-020](adr/ADR-020_LLHLS_DVR파라미터.md) §3-갱신)에서 미업로드 삭제=어디서도 서빙 불가이므로 이 조건은 필수.
3. **`duration_ms`는 실측값**을 넣는다(키프레임 위치상 목표 4000과 다를 수 있음). 매니페스트 `#EXTINF`는 이 값을 쓴다.
4. **`seq`는 재사용·재정렬하지 않는다**(멱등·캐시 안전).

## 4. 소유·경계

| 항목 | 소유 |
|---|---|
| 테이블 DDL·마이그레이션·인덱스 전략 | **3번**(데이터 계층 오너) |
| INSERT/UPDATE(세그먼트 생성·업로드 확인·로컬 정리) | **1번**(Media Origin / 업로더) |
| 매니페스트 생성 시 SELECT | **1번** |
| 클립 구간 조회 SELECT | **3번**(Clip Service) |

- **쓰기 경로가 1번, 스키마 소유가 3번**이라 컬럼 추가·타입 변경은 **3번 승인** 필요(공통 규칙: 스키마 변경 최종 승인권=3번).
- 세그먼트 바이너리는 **절대 PG에 넣지 않는다**(S3만 — 10-데이터플로우 원칙).

## 5. 미확정 (3번 리뷰 항목)

- 파티셔닝 필요 여부(방송당 900행/시간 → 장시간·다수 동시 방송 시 증가율)
- 보관 정책: `broadcasts.vod_expires_at`(60일, [ADR-004](adr/ADR-004_DVR_VOD보관.md)) 만료 시 이 행들도 함께 정리하나
- `upload_state` enum vs boolean + 실패 카운트 컬럼
- Redis 캐시 필요 여부(라이브 매니페스트가 4초마다 900행 조회 → 캐시 or 증분 갱신 전략)
  - **[2026-07-27 부분 답]** 라이브 매니페스트는 **평시 DB 조회 ~0**으로 설계: 콜드 프리픽스는 매니페스트 레이어의 **메모리 캐시**(세그먼트 완성 push로 4초당 1회 증분 갱신, 폴링 없음), DB SELECT는 재시작 복구·장애 인계·VOD 확정 때만. 라이브 경로엔 Redis 캐시 불필요할 가능성 큼 — 3번 리뷰 시 참고.
