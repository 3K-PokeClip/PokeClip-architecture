# ADR-019: 스트림 키 형식·발급·전달 규약 (streamid / passphrase)

> For future Claude: PokeClip 설계 결정. 상태=**채택**(2026-07-24, kty 확정). [ADR-018](ADR-018_스트림키저장.md)이 "어디에 저장하나"를 정했다면 이 ADR은 **"어떤 형식이고, 어떻게 발급·전달·폐기하나"**를 정한다. 핵심 3가지 — ① streamid=`#!::r=<26자 Crockford Base32>,m=publish` / passphrase=32자 랜덤·AES-256 ② **방송 중 재발급 차단(MVP)** ③ 자격증명 전달=**페어링 코드**(플러그인 OAuth 불필요). 관련 [ADR-001](ADR-001_송출프로토콜.md)·[ADR-002](ADR-002_OBS플러그인.md)·[ADR-012](ADR-012_계정권한.md)·[ADR-018](ADR-018_스트림키저장.md).

## 컨텍스트

[ADR-018](ADR-018_스트림키저장.md)이 스트림 키의 **저장 위치**(streamid=해시/PG, passphrase=원문/Secrets Manager)를 정했으나 **구체 형식값·발급 규칙·전달 방식은 미정**으로 남겼다. M1 0단계 "SRT 입력 규약" 계약을 확정하려면 이 셋이 필요하다.

논의 중 확인된 **SRT 프로토콜 사실**(구현 시 libsrt 문서 재검증 권장, confidence: high):

- **streamid는 평문 전송된다.** 암호화 성립 *이전* 핸드셰이크에서 서버가 읽어야 라우팅·인가가 가능하기 때문. SRT Access Control 문서도 "streamid에 비밀을 넣지 말라"고 경고한다. → **streamid는 비밀이 아니라 "식별자"**다.
- **passphrase는 전송되지 않는다.** 송신자가 미디어 암호키(SEK)를 passphrase로 유도한 KEK로 감싸(wrap) 보내고, 수신자가 자기 passphrase로 **풀 수 있는지**로 검증한다(AES Key Wrap 무결성 검사). 즉 **검증 = 대조가 아니라 "복호화 성공 여부"(소유 증명)**.

→ **보안 무게는 전적으로 passphrase에 있다.** streamid만으론 송출할 수 없어야 한다.

## 결정

### 1. 형식값

| 값 | 형식 | 비고 |
|---|---|---|
| **streamid** | `#!::r=<stream_token>,m=publish` | SRT Access Control 표준 문법(libsrt·MediaMTX 등 호환), `m=publish`로 송출 모드 명시 검증 |
| `stream_token` | **26자 Crockford Base32**(0-9, A-Z 中 I·L·O·U 제외), 128bit 랜덤 | 혼동 문자 없음(복사·구술 안전), **의미 없는 불투명 값**(평문 노출되므로 신원 유추 불가해야) |
| **passphrase** | **32자 랜덤**, **AES-256**(`SRTO_PBKEYLEN=32`) | **libsrt 공식 검증 완료(2026-07-24)**: `SRTO_PASSPHRASE`는 *"minimum 10 and maximum 80 characters"* → 32자는 안전 구간. `SRTO_PBKEYLEN`은 `0/16(AES-128)/24(AES-192)/32(AES-256)` 허용 → **32 정식 지원**. 출처: [SRT API socket options](https://github.com/Haivision/srt/blob/master/docs/API/API-socket-options.md). **스트리머별 고유**(공용 금지 — [ADR-018](ADR-018_스트림키저장.md)에서 기각) |

**불변식: `streamid`는 공개 식별자(평문 전제), `passphrase`는 비밀(전송 안 됨).** streamid에 사용자명·이메일·채널명 등 개인정보를 넣지 않는다. "streamid만 있으면 송출 가능"한 설계는 금지.

### 2. 재발급(로테이션) — **방송 중 변경 불가 (MVP)**

- **방송 중에는 재발급을 차단**한다. 재발급은 **방송 종료 후에만** 가능.
- 재발급 시 **기존 키 즉시 무효**(active=false + Secrets 삭제).
- **긴급 유출 대응 경로**: 방송 중 유출이 의심되면 **방송을 강제 종료시킨 뒤 재발급**한다(재발급 자체를 방송 중 허용하는 대신, 종료 → 재발급 2단계).
- **MVP 단계의 단순화 선택**이다. 유예(grace) 병행 방식은 상태 관리·보안 창이 늘어 MVP엔 과하다고 판단. 운영 데이터가 쌓이면 재검토.

### 3. 자격증명 전달 — **페어링 코드 방식**

```
① 대시보드(웹, 이미 로그인 상태)에서 단발 페어링 코드 발급·표시
② 스트리머가 플러그인에 코드 1회 붙여넣기
③ 플러그인이 코드를 우리 API에 제출 → 연결정보(host·port·streamid·passphrase) 수신
④ 코드는 사용 즉시 소멸 + 단시간 만료
```

**페어링 코드 구체값** (2026-07-24 확정):

| 항목 | 값 |
|---|---|
| 코드 형식 | **8자 Crockford Base32**, 표기 `XXXX-XXXX` (약 40bit) |
| 만료 | **10분** |
| 재사용 | **일회용** — 교환 성공 즉시 소멸, 재요청 거부 |
| 발급 rate limit | **계정당 분당 3회** |
| 교환 rate limit | **IP당 분당 5회** + 실패 누적 시 차단 |
| 바인딩 | 발급한 **계정에 묶임** — 교환해도 그 계정의 자격증명만 발급 |

> **불변식: 코드 길이·만료·교환 rate limit은 세트로만 유효하다.** 8자(40bit)는 그 자체로는 짧지만 *10분 만료 + 교환 rate limit*과 결합해야 brute-force 안전성이 성립한다. **셋 중 하나를 완화하려면 나머지를 조여야 한다.**

- **플러그인은 OAuth를 구현하지 않는다.** C++(libobs)로 브라우저 열기·로컬 콜백·토큰 갱신을 짜는 부담을 피한다(M1 일정 보호).
- **요구 충족 근거**: `2_UserJourney`의 요구는 "**매 방송 반복 설정 0회**"이지 "온보딩도 0회"가 아니다. 온보딩 1회 코드 입력은 [ADR-002](ADR-002_OBS플러그인.md) 무설정 UX와 충돌하지 않는다.
- **SRT URL 통째 복붙 금지** — URL에 passphrase가 평문으로 노출되어 화면 공유·로그로 새므로 [ADR-018](ADR-018_스트림키저장.md) 원칙과 충돌.

## 근거

- **표준 문법 채택** — SRT Access Control 규약을 따르면 libsrt·MediaMTX 등 표준 도구와 호환되고, 서버가 mode·resource를 명시적으로 파싱·검증할 수 있다([ADR-003](ADR-003_미디어서버_Go.md)이 MediaMTX를 참조 레퍼런스로 삼는 것과도 정렬).
- **Crockford Base32** — 대소문자·혼동 문자(I/L/O/U) 제거로 사람이 복사·구술해도 오류가 없다. 페어링 코드 UX와 잘 맞는다.
- **방송 중 차단(MVP)** — 유예 병행은 "기존 키를 잠시 살려두는" 상태를 만들어 구현·보안 검증 부담이 늘어난다. **방송 강제 종료라는 긴급 경로가 있으므로 안전 하한은 확보**되고, MVP는 단순함을 택한다.
- **페어링 코드** — 플러그인 구현 비용이 압도적으로 낮고, 코드가 단발·단시간이라 오히려 토큰 저장·갱신보다 관리면이 작다.

## 검토한 대안

- **재발급 유예 N분 병행**: 진행 중 방송이 안 끊기는 장점. 그러나 MVP엔 상태 관리·보안 창 부담 → **보류**(운영 후 재검토). *(kty 판단: MVP 단계라 단순화 우선)*
- **재발급 즉시 폐기(방송 중에도 허용)**: 보안 최우선이나 진행 중 방송이 그 자리에서 끊김. 방송 중 차단 + 강제종료 경로로 동일 효과를 얻으면서 사고성 끊김은 없앰 → 기각.
- **플러그인 구글 OAuth 자동 fetch**: 완전 0단계 UX지만 C++ 플러그인에 OAuth 전체 흐름(브라우저·콜백·토큰 갱신) 구현 필요 → M1 일정 부담으로 기각. **계약만 유지하면 후일 업그레이드 가능.**
- **SRT URL 한 줄 복붙**: 구현 최단이나 passphrase 평문 노출 → 기각.
- **passphrase 미사용(암호화 없이 streamid만)**: 전달이 단순해지나 streamid가 평문이라 도청자가 그대로 송출 가능 → **인증이 무력화됨**. 기각.
