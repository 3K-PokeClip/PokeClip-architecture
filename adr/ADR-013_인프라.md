# ADR-013: 인프라 (CA) — ECS Fargate + Media EC2, HA 실적용

- **상태**: 채택
- **결정일**: 2026-07-20
- **관련**: [ADR-003](ADR-003_미디어서버_Go.md) · [ADR-014](ADR-014_비용모델.md)
- **반영 산출물**: 5_CA

## 컨텍스트

소마 지원금 전제(비용은 "너무 심하지만 않으면" 제약 아님)에서, 코어 서비스의 배포 형태(EC2 vs ECS)와 가용성 수준, 배포 파이프라인, CDN 구성을 정한다. 어필·안정성 우선.

## 결정 묶음

- **Core = ECS Fargate 5서비스**: 서비스별 독립 배포, 태스크 자동 복구, Render·AI 워커는 큐 길이 기반 오토스케일(min 0). **Media Origin은 EC2 단독** — 진행 중 SRT 연결·DVR 버퍼를 가진 스테이트풀 UDP 워크로드라 오케스트레이션에 부적합(의도적 제외, 그 판단 자체가 설계 근거).
- **SRT는 UDP라 L7 LB(ALB) 불가** → Media EC2는 Public Subnet + EIP 직수신(보안그룹 제한). HLS 시청 경로는 CDN이 앞단 차단.
- **HA 실적용**: RDS Multi-AZ(자동 페일오버 1~2분), ElastiCache primary+replica(자동 승격), CloudWatch 알람(CPU·큐 적체·인제스트 다운→Discord)+대시보드. 인제스트는 스테이트풀이라 '피해 최소화'(세그먼트 즉시 S3 적재+플러그인 자동 재연결), SRT 이중 경로는 향후 확장으로 문서화.
- **dev 스테이지 AWS 운영**: dev ECS(최소)·RDS micro·dev S3/SQS — main push 자동 배포 대상, 통합 테스트 실환경. 개발 루프는 로컬 docker-compose 병행.
- **모노레포**: plugin·media·core·chat·ai·web 한 저장소, CI 경로 필터로 변경 서비스만 빌드. 기존 수집기는 /chat으로 흡수(원본 레포는 발전 증거로 보존). GitHub Actions→ECR→ECS 롤링(Core)/SSM(Media), main→dev 자동·release tag→prod 수동 승인, 플러그인은 3-OS 빌드→GitHub Release.
- **CDN 분기 2 병기**: A본선 Akamai AMD(LL-HLS 딜리버리 공식 지원, 현직 멘토 협력으로 캐시 정책·토큰 인증 구성 — 계약제라 확보가 선결 조건) / B폴백 CloudFront(무료 1TB, 세그먼트 불변 장TTL·매니페스트 초단위 TTL). 오리진: 라이브=Media EC2, VOD·클립=S3.
- **AWS build-vs-buy**: 차별화 계층(인제스트·세그먼터·LL-HLS/DVR·렌더·자막)은 직접 구현 — MediaLive+MediaPackage+MediaConvert+Transcribe로 대체 가능함을 알고도 의도적 배제(핵심 역량 증명 + 시간당 과금 회피). 비차별화 인프라(RDS·ElastiCache·S3·SQS·CDN·CloudWatch·Secrets)만 관리형.

## 검토한 대안

- **EC2 2대(코어 전 서비스 수동 배치)**: 초기 검토안. 최저 비용이지만 배포·복구·스케일이 전부 수동, 서비스 5개의 독립 배포 불가. 비용이 제약이 아니라는 전제가 확정되며 탈락.
- **EKS(쿠버네티스)**: 오케스트레이션 어필은 크나 3인 팀 운영 부담(클러스터 관리·업그레이드)이 프로젝트 본질(미디어 파이프라인)을 잠식 → 탈락. ECS는 같은 "컨테이너 오케스트레이션 운영 경험" 서사를 관리 부담 없이 제공.
- **MediaLive+MediaPackage 등 관리형 미디어**: 차별화 계층을 통째로 외주화 — "만든 사람" 서사 상실 + 시간당 과금 → 의도적 배제(ADR-003과 동일 맥락).
