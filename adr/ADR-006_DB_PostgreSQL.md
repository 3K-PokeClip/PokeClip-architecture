# ADR-006: DB — PostgreSQL (+ JSONB)

- **상태**: 채택
- **결정일**: 2026-07-20
- **관련**: [ADR-007](ADR-007_스택배치.md) · [ADR-009](ADR-009_클립내보내기.md)
- **반영 산출물**: 3_SA · 4_SysA · 5_CA

## 컨텍스트

코어 DB 선택. "NoSQL이 요즘 유행인데 왜 관계형인가"라는 질문에 답할 수 있어야 한다.

## 결정

코어 DB는 PostgreSQL. 반정형 데이터(레시피)는 JSONB 컬럼으로 수용.

## 근거

- 코어 데이터가 관계형 사슬: 계정→채널 연동→편집자 권한→점프카드→레시피→클립→잡 상태. "이 클립은 어느 방송의 어느 카드에서 어느 레시피로 렌더됐고 누가 승인했나"가 곧 조인. 승인 플로우 상태 전이는 트랜잭션 정합성 필요.
- NoSQL이 이기는 조건(비정형 스키마 / 단일 DB가 못 버티는 초대량 쓰기 / 단순 키-값 접근)이 전부 부재. 유일한 대량 스트림인 채팅은 S3(아카이브)+Redis(실시간 집계)로 분리 설계.
- "NoSQL 유행" 프레임 정정: 현재 업계 기본값은 "일단 Postgres"(JSONB·확장 생태계). 그리고 Redis(키-값)·S3(오브젝트)가 이미 적재적소의 NoSQL 역할 — 정합성=PG, 실시간=Redis, 대용량=S3라는 폴리글랏 퍼시스턴스가 최종 구조.

## 검토한 대안

- **MongoDB 등 도큐먼트 DB**: 레시피(JSON)엔 맞지만 권한·승인·잡 상태의 조인·트랜잭션에서 손해. 레시피는 PG JSONB로 충분히 수용 → 탈락.
- **DynamoDB**: 키-값 접근 패턴·초대량 쓰기 전제가 없고, 로컬 개발·조인 표현력에서 불리 → 탈락.
