# ADR-007: 스택 배치 — 언어별 경계 (Spring/Go/Node/Python/C++)

- **상태**: 채택
- **결정일**: 2026-07-20
- **관련**: [ADR-003](ADR-003_미디어서버_Go.md) · [ADR-006](ADR-006_DB_PostgreSQL.md) · [ADR-011](ADR-011_채팅하이라이트.md)
- **반영 산출물**: 3_SA · 4_SysA

## 컨텍스트

팀 3명(FE 1: TS+React, BE 2: Java Spring 주력), 개발은 Claude·사람은 리뷰. "굳이 Spring? 전부 Go로 해도 되지 않나"라는 질문에 답해야 하며, 언어 수가 5개인 스택이 정당한지가 쟁점.

## 결정

코어 API(Auth·Clip·Render)=Java Spring Boot, 미디어=Go, 채팅 수집·분석=TypeScript/Node(기존 자산), AI=Python(faster-whisper), 플러그인=C++, FE=React+TS(운영 콘솔은 동일 SPA 내 권한 분기).

## 근거

- 팀 전제: 개발은 Claude, 사람(FE1·BE2)은 리뷰·운영 → 언어 기준은 "AI 생성 품질 + 사람 리뷰 가능성". 리뷰 가능성이 품질 게이트의 전부다.
- Spring 코어 유지 이유는 성능이 아님(성능은 Go 근소 우위나, 코어 API 규모에선 무의미 — 성능 크리티컬 지점인 미디어·렌더에는 이미 Go·FFmpeg 배치). 실제 이유: ①BE 2인의 촘촘한 리뷰 ②비즈니스 백엔드에서의 Spring 생태계 생산성 ③커리어 커버리지 — Spring 코어+Go 미디어면 Java 카드와 Go 카드를 동시 보유(Go 회사엔 "Go로 미디어 엔진"이 CRUD 경력보다 강함).
- Node 유지: 기존 streaming-chat-collector(Fastify+Socket.io, 치지직 공식 OAuth+비공식 WS 이원 어댑터) 재사용. FE도 TS라 유지보수 인력 겹침.
- 언어 수를 늘리는 것은 경계가 명확할 때만 정당 — 각 언어의 채택 이유가 한 문장으로 방어 가능해야 한다.

## 검토한 대안

- **전부 Go 단일화**: 성능 관점 이득은 코어 API 규모에서 무의미하고, BE 2인의 Java 리뷰 역량을 버리게 됨 + 채팅 기존 자산(Node) 재작성 비용 발생 → 탈락.
- **전부 Spring 단일화**: 미디어 계층(고루틴 파이프라인·저수준 바이너리 처리)과 AI(faster-whisper 생태계)에서 언어 적합성 손해 → 탈락.
